# ERPNext helpers internals

Moved out of the root CLAUDE.md so it loads only when the work touches this area. Notes for contributors and AI agents; the root file keeps the rules that apply everywhere.

- **ERPNext helpers (T3.4, `ffc erp`; docs/cli/erpnext.md).** Source checked: ERPNext v15.121.6 and v16.37.0 branch heads, Frappe v15/v16 heads (not the exact image versions). PR 1 is `erp map`, PR 2 `erp payment`, PR 3 the lookups `erp item`, `erp stock` and `erp party` (last paragraph); PR 4 is the MCP `erp` tool set (end of this paragraph). Mappers have no `methods=`, so a GET is allowed and a GET never commits (frappe app.py): mapping over GET leaves nothing behind. They are `(source_name, target_doc=None, args=None)` (Delivery Note's third is `kwargs`), return one unsaved doc (`__islocal`, no real name) and check create on the target and read on the source. Same paths on v15 and v16 (`erpMapperMethods`, client/erpnext.go:26; table by major at :40, so a new major is one row): Quotation to Sales Order, Sales Order to Sales Invoice and Delivery Note, Delivery Note to Sales Invoice, Purchase Order to Purchase Receipt and Purchase Invoice, Purchase Receipt to Purchase Invoice, Material Request to Purchase Order. Sales Order to Purchase Order is out (a list, one per supplier). Develop (17) moved most mappers to `<doctype>/mapper.py`, so only 15 and 16 ship. **Never send `ignore_permissions`** (v16 mappers take it; `MapDoc` sends only `source_name`; `TestERPMapNeverSendsIgnorePermissions`). Quotation to Sales Order for `quotation_to` Lead/Prospect inserts a Customer inside the call (rolled back over GET), so `refuseLeadQuotation` reads the Quotation first and refuses with a StateError (exit 6) unless a Customer already points at the lead or prospect (`lead_name`/`prospect_name` = the Quotation's `party_name`; `_make_customer` reuses it, quotation.py v16:598-606, v15:593-601; a 403 reading Customers counts as none). ERPNext check: `erpNextMajor` (erp.go) from `serverInfo` (cached 24 h); no `erpnext` app is an `APIError` 404 (exit 4, "ERPNext is not installed on <site>"), a major other than 15/16 is exit 1 pointing to `ffc api`, an unknown pair a usage error listing the pairs. Flow (`runERPMap`, erp_map.go): checks and reads first, then map (GET), then with `--create` `createFromDraft` (erp.go, shared with payment): `InsertableCopy` (drops `__` keys top level and in child rows, and a null or empty `name`; the mapper's draft has no top-level name and child rows with parent null plus parenttype, parentfield, idx, which stay; only lists of documents, items with a `doctype`, are walked) and `CreateDoc`; `--submit` implies it, runs `refuseWorkflow(target, "")` before the insert, then `SubmitDoc` (a submit failure returns the created document too: `printMapped` prints it as a created one, so a script gets its name, and the wrapped error keeps the exit class; an insert answered without a name is an error, no submit). Default prints the draft and writes nothing. `--dry-run`: the mapping GET runs, the insert is held back as a `DryRunError`, and `planSubmit` (erp.go) adds the `frappe.client.submit` plan (the insert has no name to submit). Fake: `HandleMethod(<mapper path>, …)` plus `SetApps` with an `erpnext` entry (`erpTSite`, erp_test.go; it points `sitecache.UserCacheDir` at a temp dir per site, since the version cache is keyed by site name and URL). Contract: `contractERPMap` (contract_erp_test.go) first runs `contractERPSetup`: a Company must exist, else `frappe.desk.page.setup_wizard.setup_wizard.setup_complete` is POSTed once with `args` (language "English", country, timezone, currency, full_name, company_name, company_abbr, chart_of_accounts "Standard", fy_start_date/fy_end_date of the current year; no email, so no user is made; `setup_demo` is async and not used) under a 5 minute client timeout, since frappe_docker's pwd.yml never runs the wizard; it runs only on a loopback site URL or with `FFC_CONTRACT_ERP_SETUP=1` (else the subtest skips), accepts only a `{status: ok}` reply (a 5xx or transport error, e.g. the 120 s proxy limit, falls through to polling Global Defaults `default_company`, the wizard's last step), and the ctx for the rest is made after it. It then creates a Customer, a non-stock Item and a submitted Sales Order with unique names and maps it to a submitted Sales Invoice. Verified in CI (run on 69aed92, v15 and v16): setup_complete answers `{status: ok}` within seconds with these args, and the SO to SI map inserts and submits; Float fields arrive as `2.0`, so compare quantities numerically. **`erp payment --against "DT:NAME" [--amount N] [--bank-account A] [--reference-date YYYY-MM-DD] [--create] [--submit] [--keys] [--dry-run]`** (erp_payment.go, `runERPPayment`): `erpnext.accounts.doctype.payment_entry.payment_entry.get_payment_entry(dt, dn, party_amount=None, bank_account=None, bank_amount=None, party_type=None, payment_type=None, reference_date=None, created_from_payment_request=False)` (v15.121.6:2901, v16.37.0:2898, same signature, no `methods=`, so GET; it never inserts; `frappe.has_permission("Payment Entry", create, throw)` and `doc.check_permission()` first; no `ignore_permissions` parameter). ffc sends only `dt`, `dn` and the flags given (`--amount` is a positive decimal without leading zeros, checked by `plainAmount` and sent as a plain string, `party_amount`; Frappe coerces it for its `int | float` check, as for any GET query value; `--bank-account` is `bank_account`; `--reference-date` is `reference_date`), never `bank_amount`, `party_type`, `payment_type` or `created_from_payment_request`. DocTypes (`client.PaymentDocTypes`, checked before any request, else usage error exit 2; `set_party_type` is an UnboundLocalError 500 for any other): Sales Invoice, Sales Order, Purchase Invoice, Purchase Order, Dunning (v15 and v16 both handle it). Flow: `erpNextMajor`, `PaymentMethod(major)`, `PaymentDraft` (GET), then the same tail as map (`createFromDraft`, target "Payment Entry"). Errors: the only `frappe.throw` on the document is "Can only make payment against unbilled <dt>" for a Sales/Purchase Order with per_billed over 100 + the over_billing_allowance (ValidationError 417, exit 6; a blocked Supplier is also 417); 403 is exit 5, a missing document 404 is exit 4. **A missing default bank or cash account does not throw** (the plan said it did): `get_bank_cash_account` returns an empty `_dict`, the draft comes back with `paid_from` or `paid_to` empty (both reqd), and the insert would fail as a missing value. So `paymentAccountGap` makes the default output carry a stderr `warning:` and `--create`/`--submit` a `StateError` (exit 6) before any write. An invoice with nothing outstanding is not refused by the method (`set_payment_type` gives Pay, paid amount 0); what the insert does then is the server's validation (UNVERIFIED). A Mode of Payment on the document overrides `--bank-account` (the mode's account replaces `account`, journal_entry.py:1363), so `bankAccountOverride` compares the draft's bank side (`paid_to` on Receive, `paid_from` on Pay) with the flag and warns on stderr when they differ (the warning also comes with a created entry). Lookup order in `get_default_bank_cash_account`: `--bank-account` (account) if given, the Mode of Payment account when the document has `mode_of_payment`, else the Company `default_bank_account` or the single non-group Bank account, then the same for Cash with `default_cash_account` (set by the setup wizard from the chart's "Cash" account through `Company.set_default_accounts`; unverified in CI). Fake: `HandleMethod(get_payment_entry, …)` plus `AddDocType("Payment Entry")` (`erpPSite`, erp_payment_test.go, on top of `erpTSite`). Contract: `contractERPPayment` (after `contractERPOrder`, the fixtures shared with `contractERPMap`): maps a Sales Order to a submitted Sales Invoice, makes sure the Company has a default cash account (sets it from the chart's one Cash account when empty) and passes it as `--bank-account` (a default bank account would need a reference number), checks the draft, then `--submit`, the Payment Entry reference and `outstanding_amount` 0; restores the Company's `default_cash_account` in `t.Cleanup` when it set it, and registers the Payment Entry cleanup as soon as its name is printed (also when the submit failed after the insert); written without a run against a site (UNVERIFIED until CI). `erpLines.created`/`submitted` are funcs of the name, so a `%` in a document name never reaches a format string. **Lookups (PR 3; erp_lookup.go, client/erpnext_lookup.go; all GETs, no `methods=`, never `ignore_permissions`, `LookupFor(major)` table).** `erp item ITEM --company C [--doctype DT] [--customer X | --supplier X] [--price-list P] [--qty N] [--warehouse W] [--date D]` is `erpnext.stock.get_item_details.get_item_details`; its first parameter is `args` on v15 (v15.121.6:60) and `ctx` on v16 (v16.37.0:85, `@erpnext.normalize_ctx_input`, `ItemDetailsCtx = frappe._dict`, no alias), and ffc sends the dict as a JSON string under the right name (`LookupMethods.ItemParam`; tests assert the query per major). Needs `company` (else "Please specify Company"), `doctype` (the meta of `<DocType> Item` is read, so ffc allows only `ItemSalesDoctypes`/`ItemPurchaseDoctypes`; default Sales Invoice, Purchase Invoice with `--supplier`; `--customer` needs a sales DocType, `--supplier` a purchase one) and `item_code`; with a `currency` field on the DocType, `validate_conversion_rate` throws "Exchange Rate is mandatory" for a missing `conversion_rate`, so ffc always sends `conversion_rate` and `plc_conversion_rate` as 1 (ffc sends no `currency`, so `get_exchange_rate(None, ...)` returns None at once and `or 1.0` keeps 1, get_item_details.py:1340-1343 on v15; no exchange-rate call happens), so a price list in another currency is not converted (documented). `qty` defaults to 1 (a new row's quantity; pricing and packing units use it), `rate` is never sent (with a price list ERPNext may insert an Item Price), `--warehouse` goes as `set_warehouse` because `get_item_warehouse` ranks it first and the Item/Item Group/Brand defaults above a plain `warehouse`. `price_list` is read by `process_args`/`_preprocess_ctx` the same way as `selling_price_list`. `erp stock ITEM --warehouse W [--date D] [--valuation]` is `erpnext.stock.utils.get_stock_balance` (utils.py:98 v15, :96 v16; checks only `Item` read, not the warehouse): answers a number, or `[qty, rate]` with `with_valuation_rate` (sent only as `true`: v16's parameter is untyped, so a `0` would be truthy); a `--date` sends `posting_date` plus `posting_time` 23:59:59 (the default time is now, which would drop the later entries of that day); the output is `{item_code, warehouse, actual_qty, valuation_rate?, posting_date?}`. Without `--warehouse` it is `erpnext.stock.dashboard.item_dashboard.get_data(item_code, start, sort_by, sort_order)`: one Bin row per call of `limit_page_length=21` (v15 and v16), rows only for Bins with some non-zero quantity; ffc pages with `start` 0, 21, ... up to `StockMaxPages` = 24 (504 rows, then a stderr warning), sorts by `warehouse asc` (unique per item, so pages do not overlap; the default `actual_qty desc` ties), and `html.UnescapeString`s `item_code`, `item_name`, `stock_uom` and `warehouse` (the method `escape_html`s them). `truncated` is true only when a 25th probe page past the cap still has rows. Both stock paths answer 0 / `[]` for an unknown item or warehouse (utils.py:98-143; `get_item_details` and `get_party_details` do 404), so `stockTargetsExist` reads the Item (and the Warehouse; a 403 there is skipped) first and a typo is exit 4; with a Warehouse user permission both versions limit the rows to `frappe.get_list("Warehouse")`, 20 at most. v15's `get_data` has no Bin read check (it uses `frappe.db.get_all`, only the Warehouse user permissions apply), v16's returns `[]` without Bin read: documented. `--date`/`--valuation` without `--warehouse` are usage errors (the rows have no date; they carry `valuation_rate`). `erp party (--customer X | --supplier X) [--company C] [--date D] [--doctype DT]` is `erpnext.accounts.party.get_party_details` (party.py:77 v15, :78 v16; same parameters, v16 adds a whitelisted `ignore_permissions` that is never sent and is ignored anyway: it calls `_get_party_details` with `False`); `party`, `party_type` (Customer/Supplier), `company`, `posting_date`, `doctype` only when given (an invoice DocType adds `debit_to`/`credit_to` and `due_date`; without a company the currency can fail when the party has no default). Output: a document table, or data with `--keys` (rows for stock: `--keys` per row). Fake: `HandleMethod` for the four methods (`erpLSite`, erp_lookup_test.go). Contract: `contractERPLookups` (stock Item with an Item Price on Standard Selling, a Material Receipt of 5 into the Company's Stores warehouse with the Company's `stock_adjustment_account` as difference account); cleanup is best effort (a cancelled receipt leaves Stock Ledger Entries that link the Item, so the delete can fail: the Item is then disabled and the leftover logged); written without a run against a site (UNVERIFIED until CI). **MCP `erp` tool set (PR 4; mcp_erp_tools.go, erp_input.go; docs/mcp/tools.md).** Opt-in (`--toolsets core,erp`; in `knownToolsets`, not `defaultToolsets`): `erp_map` (`from_doctype`, `from_name`, `to_doctype`), `erp_payment` (`against_doctype`, `against_name`, `amount`, `bank_account`, `reference_date`), `erp_item`, `erp_stock`, `erp_party` (the CLI flags with underscores). All are `actRead` (GET-safe methods: `read_only` keeps them) and return data only: `erp_map` and `erp_payment` answer `{draft, warnings?}` with the draft as `InsertableCopy` (ready for create_doc `data`); saving and submitting stay with create_doc/submit_doc, so confirmation, policy and audit stay in one place. The CLI and the tools share the logic and the checks: `runERPMap`, `paymentDraft` (the notes of `runERPPayment`: `paymentWarnings` gives the account gap and the bank account override as a list, joined for stderr), `runERPItem`/`runERPStock`/`runERPParty`, and `build*Options`/`buildStockQuery` over `erpInput` (`erpInput{}` = flags, `erpArgs` = tool arguments; it names inputs in messages, `--bank-account` vs `bank_account`, and the exit-1 hint, `ffc api` vs `call_method`) and `erpOpt` (given or not; a flag given blank is a usage error, a blank tool argument counts as not given). The site comes from `siteFrom(ctx)` (the version cache is per site). `erp_stock` without `warehouse` answers `{item_code, rows, truncated, warning?}`. Scope (`erpScope`, called from `scopeOf`): erp_map the source and target DocType (plus Customer for a Quotation source: the lead check reads it), erp_payment the DocType paid against and Payment Entry (+ Account with `bank_account`; the party is covered by the source document), erp_item Item, Price List (the settings' default when none is given) and Bin (+ Customer, Supplier, Warehouse when given), erp_stock Item, Warehouse and Bin, erp_party Customer or Supplier plus Address and Contact (address_display and contact fields are read without a permission check, party.py:324-335; Bin likewise in get_item_details.py:262-265); `doctype` of erp_item/erp_party (the document a row is for) is not in the scope (`erpDoctypeArgs`; it only picks the row's meta, no such document is read) and `optionalDoctype` lists both so a blank one is not refused; names go in `sc.Names`. The tools carry `jq` (all `big`). Tests: mcp_erp_test.go (`erpMCP` over `erpTSite`/`erpLSite`/`erpPSite`: both majors, the item `args` vs `ctx`, refusals, per-DocType allow/deny, read_only, multi-site). No contract subtest: the contract harness has no in-process MCP client.
