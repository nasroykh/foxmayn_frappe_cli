# MCP server internals

Moved out of the root CLAUDE.md so it loads only when the work touches this area. Notes for contributors and AI agents; the root file keeps the rules that apply everywhere.

- **MCP policy (T1.4b).** `sites.<name>.mcp` (`config.MCPPolicy`, unknown keys are an error) is read on every tool call (`env.site` = `config.LoadSite`, no network, never sets the display-format globals); `toolHandler` checks it before `env.client`, so a refused call sends nothing. Config may loosen the built-in rules (sensitive DocTypes, `deniedMethods`; Deleted Document is sensitive, and the Deleted Document `restore`/`bulk_restore` methods are denied); the `ffc mcp` flags only narrow (`mcpFlags`; passed to the detached child by `daemonArgs`). `applyEnvOverrides` and `File.PutSite` keep the `mcp` block: dropping it would widen access silently. Every call writes one audit line (`auditLog.write`: args via `client.RedactArgs`, which copies, then `data`/`args` reduced to keys and size; secret argument values are also cut out of error text, list-form filters on secret fields are redacted, and every caller-controlled string is sanitised and clipped). `scopeOf` trims DocType names and refuses invisible characters; for call_method it walks the whole args tree (JSON strings included) for `doctype`/`dt`/`ref_doctype`/… and refuses a `docMethods` call that names no DocType. `allow_doctypes` from the config needs `allow_methods` from the config: a flag list never stands in for it. Query arguments (`queryScope`, mcp_query_scope.go: list_docs/count_docs/aggregate `filters`, `fields`, `order_by`, and `filters`/`or_filters`/`fields`/`order_by`/`group_by`/… anywhere in call_method args) add the DocType of four-element filters to `sc.Doctypes` and their field references to `sc.FilterFields`/`SelectFields`; with any allow/deny_doctypes rule (`hasDoctypeRules`) `checkQueryFields` refuses a non-identifier filter field and a `.` or backtick in fields/order_by, because `link.field`, `child.field` and `` `tabX`.`f` `` join another DocType (v16 query.py ~808-847, v15 db_query). Child-table fields are refused too (no schema to tell them from a Link).

- **call_method permission bypass.** `scopeOf` puts the call_method `args` keys `ignore_permissions` and `ignore_user_permissions` (`bypassKeys`; case/space-folded, `args` object or JSON string, any value incl. false/0) into `sc.Bypass` via `callBypass`, and `check` refuses them (policy error, `auditDenied`, nothing sent, no config switch). For `run_doc_method` (any name `methodNames` matches) `callBypass` also scans its nested `args` and `arg` (reported as `args.<key>`/`arg.<key>`). Frappe facts (frappe-15/16 source): `get_newargs` (frappe/__init__.py v15 ~:1808, v16 :1190-1191) pops `ignore_permissions` and `flags` before any /api/method function runs, so the ERPNext mappers (`make_sales_invoice`, `create_dunning`, `make_timesheet`, v16 `get_party_details`) never receive `ignore_permissions` over HTTP; refusing it is defence in depth (an API Server Script reads form_dict before frappe.call, handler.py:70). `run_doc_method` forwards nested `args` to `doc.run_method(method, **args)` unfiltered (handler.py v15 :321/:361, v16 :296/:336). `ignore_user_permissions` is NOT popped and reaches `erpnext.controllers.queries.employee_query` and `frappe.desk.search.search_link`/`search_widget` (search.py; v15 turns it into `ignore_permissions` at :213-214): the real bypass. `flags` is not refused (popped by get_newargs; dropped from document data by `RESERVED_KEYWORDS`/`_reserved_keywords`). Other MCP tools send fixed request params (caller keys only inside doc bodies or `filters`). The CLI (`ffc api`, `ffc call-method`) is the operator's own and is unchanged. `checkMethodName` refuses empty names, `/`, whitespace and control/invisible characters only: other characters are escaped by `url.PathEscape` in `CallMethodFull`, and Server Script API names are not known to be limited to Python identifiers.

- **MCP confirmation (T1.4c).** `mcpPolicy.confirm` runs after `policy.check` for calls `needsConfirm` marks (delete_doc, bulk_delete, cancel_doc, bulk_submit, bulk_cancel, apply_workflow, share_doc, assign_to, rename_doc with merge; in call_method `destructiveMethods`, `widensAccess` (share.add, set_permission with a true or absent `value`, assign_to.add/add_multiple), `argMethods` by argument value, `mergeMethods` with merge). Values in the question go through `quoted` (strconv.Quote, not Sanitize: escaping keeps the real name visible); call_method shows `keyMethodArgs` first so padding cannot hide them. The audit line's `confirm` says confirmed/unsupported/never. It returns `server.NewInputRequestBuilder(state).Elicit("confirm", …).ToolResult()`; mcp-go bridges that to `elicitation/create` for pre-2026-07-28 clients, so the handler always runs twice (audit `confirm_pending`, then `ok`/`declined`). The state is `exp.nonce.HMAC(site, tool, args)` with a key per server (`mcpEnv.confirm`, one confirmer per NewMCPServer/startMCP; a nil confirmer refuses); `spend` accepts it once. A retry without a valid state asks again, never proceeds. `canElicit` reads per-request capabilities on modern requests and the session's on legacy ones (which must also implement `SessionWithElicitation`). `confirm: always` without elicitation refuses with `cliEquivalent` (shell-quoted; only the command name if a value has control characters, or a bulk name has a comma or edge spaces; bulk_delete, bulk_submit and bulk_cancel share the rule and `scopeOf` reads their names with `parseNames`, so a numeric name counts). `--confirm` only tightens; `--confirm never` is a usage error. Tests: `mcpTClient` (mcp-go in-process client, `WithProtocolVersion("2025-11-25")` for the legacy bridge).

- **Multi-site MCP (T1.6).** `mcpEnv.sites` holds the served sites (exact config names, default first; one entry, possibly "", for a single-site server). With more than one, `addSiteParam` adds a required `site` (enum) to every tool but the `siteless` ones, `siteFor` refuses a call without one, and each call loads its own site and policy; `registerTools` keeps a tool when any site's policy allows it (`anyAllows`, which allows nothing with no policies). Each site has its own cached client and mutex in `newMCPEnv`. Only the default site signs in at start (others on first call; signing in to all could outlast the detached start's 60 s). `env.site` refuses a Load result whose name differs from the pinned one (Load's case-insensitive fallback would otherwise reach another site). `mcpSites` refuses FFC_API_KEY/SECRET with several sites (`applyEnvOverrides` would put them on every site). The daemon pins the resolved list via `daemonArgs` (`--sites=` per site, CSV-quoted by `csvField`, as for every list flag); `mcp.json` has `sites` and still writes `site` (the default) for older readers. New tools get the `site` argument for free; a tool that works on the server, not a site, goes in `siteless`.

- **restore_doc (M0, v1.19).** Lifecycle set, write, not confirmed (it is the undo of delete_doc). Arguments: `deleted_document`, or `doctype` + `name` (latest unrestored deletion, `resolveDeleted`/`findDeleted` shared with the CLI); exactly one form. Frappe's `restore` (deleted_document.py:41-65, v16) requires System Manager, rebuilds the document from `json.loads(data)`, so the DocType re-created is `data`'s own exact `"doctype"` key (`deleted_doctype` is never read), and inserts it without ignore_permissions. So `checkRestore` (after checkReport in env.run) reads the record, parses `data` as a map, requires `data["doctype"]` == `deleted_doctype` exactly and refuses any other key equal to `doctype` under EqualFold (Go struct decoding folds case, Python does not), then applies `doctypeAllowed(dt, true)` (sensitive rule, allow/deny lists) to it; the approved id goes to the call through ctx (`withRestoreID`), so the record checked is the one restored. Deleted Document is in sensitiveDoctypes (an Administrator key could otherwise forge one with create_doc/update_doc); restore_doc checks Deleted Document against deny_doctypes only (`doctypeDenied`), never against allow_doctypes, so operators never unlock writes to it. Lookup errors are audited as error, refusals as denied; the audit line names both DocTypes and the Deleted Document id.

- **Embedding the MCP server (M0, v1.19; desktop V1).** `NewMCPServer(ctx, MCPOptions)` builds what `ffc mcp` serves, through the same validation (`cleanMCPOptions`, shared with the flags; option-field names in errors, never usage errors) and construction (`buildMCP`); no package global is read on its path. Process-wide exceptions (documented on it): client.Timeout, client.Debug, the plain-HTTP warning, FFC_API_KEY/SECRET/URL; stderr still gets config/client/refresh/audit diagnostics. `Close` is idempotent and nil-safe and makes later calls fail ("MCP server closed", rechecked under the site lock, so no new login). Any main that embeds it must call `RunJQChildIfRequested()` first: `runJQ` re-executes `os.Executable()` with FFC_JQ_CHILD. `Classify(tool, args)` answers before a call: action, `Confirm` (needsConfirm), `Mode`, `WillAsk` = Confirm && no pre-request refusal && Mode == always (under if-supported a client that cannot elicit runs the call with no question, so WillAsk is false and the caller shows its own card; an app that wants ffc's question to be the card passes `Policy.Confirm: always`, which tightens even a site's `never`), Site, scope, `Denied`. `run_report` with `prepared` or `fresh`, no `prepared_report` and a site that is not read-only is classed `write` (`preparedMayStart`): it inserts a Prepared Report and queues a job, so an embedding app asks first; `toolActions` and the annotation still say read. It round-trips args through JSON like a real call, runs the tool's own handler under an unexported classify marker that stops after `env.prepare` (site, parse, jqArg, scopeOf) with no request, login, audit line or confirm state, errors when the handler did not see the marker (a replaced tool), and recovers panics; checkReport, checkRestore and checkCommentAuthor run only on the real call. `TestClassifyMatchesCall` pins parity with real calls over eliciting and non-eliciting in-process clients. `WithRunID(ctx, id)` adds `run_id` (clipped, sanitised) to audit lines, both lines of a confirmation round trip included; only a Go context value, so outside clients cannot set it (mcp-go's in-process transport passes the caller's ctx).

- MCP limits: results over 512 KiB are refused with a hint to narrow them (list_docs and run_report rows are cut to fit instead, see T2.7); `run_report` defaults to 500 rows; bulk tools take at most 200 items, in order unless `concurrency` (at most 4) is given (`bulk_create` `atomic` is one insert_many request instead, never with `concurrency`); `--read-only` registers only read tools (call_method counts as a write).

- The MCP detached-server state file is `~/.config/ffc/mcp.json` (pid, port, site, started_at, log_path, token, instance; 0600, the token is the HTTP bearer secret), guarded by a lock file; the log is `~/.config/ffc/mcp.log`. `ffc mcp stop --force` stops a PID that is alive but not health-confirmed.

- **`ffc mcp install` (T3.5, `internal/mcpinstall`).** One stdio entry in a client's user config. **Never edit `~/.claude.json`** (Claude Code rewrites it; `$CLAUDE_CONFIG_DIR/.claude.json` when set): it is only read, to decide up to date / replace, and `claude mcp add-json --scope user <name> <json>` makes the change (claude 2.1.291: add-json fails "already exists in user config", so a replacement runs `claude mcp remove --scope user` first, and when the state file was unreadable Apply retries that way on that message; `claude mcp get` has no `--scope` and starts the server, so it is not used). claude add-json is never run through a `.cmd`/`.bat` shim (cmd.exe re-parses the JSON). JSON/JSONC (claude-desktop, cursor, vscode) is edited with **hujson as a tree** (`editJSON`): no `Format()` (it would reformat the whole file), the new member gets the file's indentation, a comment after the old last member stays on its line, the trailing-comma style is kept, a strict JSON file must stay strict, and an entry equal in value is left as it is. VS Code uses `servers`, the others `mcpServers`; Claude Desktop entries get no `type`. **Codex config.toml is edited as text** (`editTOML`), never decoded/re-encoded: the scanner follows strings, multi-line strings and multi-line arrays so a `[` inside a value is not a header; it replaces `[mcp_servers.<name>]` plus its sub-tables (quoted header keys are understood) or appends, and **refuses** `mcp_servers` as an inline table, dotted keys, keys under `[mcp_servers]` or `[[...]]`. **Never clobber a file that does not parse**: refuse with the parse error (empty file = `{}`). The command is the **absolute path of the running binary** (`os.Executable` + EvalSymlinks; a go-build dir under the temp dir is refused), `--site` is pinned to `SiteConfig.Name` (only when the flag is given, not FFC_SITE), and a non-default config (`configPath` from `-c` or FFC_CONFIG) is added as `--config <abs>` before it. Names may not start with `-` (positional argument of the claude CLI, which has no `--` there). `editJSON` splits the extra before a closing brace only at a line break outside block comments (`lastLineBreak`), uses the file's line ending, and `checkJSONResult` re-parses the result and refuses unless `<topKey>.<name>` holds the entry. `Change.Check()` (claude missing or a `.cmd` shim, read-only file) runs before the prompt and again in Apply, before any backup; the claude errors carry the commands to run by hand. Apply re-reads the file and refuses if it changed since Plan, backs up to `<path>.ffc-<YYYYMMDD-HHMMSS>.bak` (O_EXCL, counter on collision), writes with `config.WriteFileAtomic` keeping the mode. **`ffc mcp uninstall` / `PlanRemove`** reuse all of it in reverse: `removeJSON` cuts byte ranges out of the source (`memberCuts`, offsets from the hujson parse): a member on lines of its own loses those lines from the break before to the break after, a comma-first comma goes with its line, a block comment spanning lines that starts or ends on the member's line stays (`firstCut`/`lastCut`), a member sharing a line loses only itself, its comma and the blanks after it (the next member's comment stays), an emptied object becomes `{}`, the top key stays, `null` is nothing to remove; `checkRemoveResult` refuses unless the result parses, stays strict, lacks `<topKey>.<name>`, every other member is byte-identical, and every comment outside the member's own lines (raw `\n` bounds; a comment crossing them counts as outside) is still there and none is new (`jsonComments`); `removeTOML` drops the entry's tables (`tomlEntrySpans`, shared with editTOML) and collapses the blank lines left behind; claude-code plans `claude mcp remove --scope user <name>` only when the state file shows the entry, or cannot be read (then claude's `No MCP server named "<name>" in user scope`, exit 1 on 2.1.291, English text, is success: `absentOK`, and Apply sets `Change.Absent`, which the CLI reports as nothing removed, `changed`/`applied` false); a remove runs through a `.cmd`/`.bat` shim (no JSON, ValidName-safe name), add-json never does. Nothing to remove = `Changed()` false, also for a missing file (`Change.remove`). Only a symlinked config is resolved (`resolveLink`; EvalSymlinks on any path would expand Windows 8.3 names). Tests: `mcpinstall.Env` over a temp dir for every GOOS layout; cmd tests set HOME, USERPROFILE, APPDATA, XDG_CONFIG_HOME and swap `mcpInstallEnv` (fake LookPath/Run) and `mcpInstallExecutable` (the test binary lives in go-build). Claude Desktop's Windows MSIX package (family `Claude_pzs8sxrjxfjjc`) has its own copy of %AppData%: `claudeDesktopPath` takes `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json` when it exists, then the real `%APPDATA%` file (an existing file there is used in place), then the package location when the package is installed (seen on a real install, 2026-10-06; tests set LOCALAPPDATA). Cursor's and VS Code's Windows paths were checked on a real install (2026-10-07: both editors keep their servers there). Unverified: the VS Code paths on macOS and Linux (inferred), CODEX_HOME (checked against codex-cli 0.160, not in the docs).

- MCP `run_report` returns only `columns`, `result`, `report_summary` (if non-null), `total_rows` and `truncated` (`compactReportResult`), plus `prepared_report: {name, finished}` for a prepared result; a prepared job still running is `{status, prepared_report: {name}, hint}` instead. CLI `run-report --json` returns the full response; `--limit` applies to both table and JSON.

- **MCP surface (T2.7).** `registerTools` drops tools by policy and `--toolsets` (`env.toolsets`, nil = `defaultToolsets` core,lifecycle; sets from `toolSurface`, `list_sites` always kept), then `describeTools` sets each tool's title (Tool.title and the title annotation) and `_meta` `anthropic/maxResultSizeChars` = `maxToolResultBytes` on `big` tools, then `registerSurface` adds resources, prompts and the instructions (`server.WithInstructions(text)(s)` after registration, so they describe only what is registered). A resource read must go through the tool handler (`resourceReader` calls `s.ListTools()[tool].Handler` with `withResourceRead(ctx, …)`, which toolHandler fills with the call's status and cause), never a separate client path: that is the site check (`siteFor`, exact then unique case-insensitive), `scopeOf`, policy, audit (`via: "resource"`, omitted for tool calls, so old readers are unaffected) and size cap. The URI template regex rejects extra segments and bad `%` escapes before our handler (JSON-RPC "resource not found", no audit line). mcp-go v1.1.1 turns every resource handler error into -32603 (handleReadResource), so a failed read keeps the tool's message and only wraps a class for OnError hooks (`classedError`: `server.ErrResourceNotFound` when `classify` says not found, `mcp.ErrInvalidParams` for denied/invalid). The instructions gate every line that names a tool on `has(tool)` and list only registered resources. Prompts make no site calls, are offered only when their `needs` tools are registered, and drop optional steps (`when(has(t), …)`); argument values go in as `promptJSON` (JSON, unprintable runes as \u escapes), and a value over its `maxLen` is refused, never cut. `list_docs` too large → the largest prefix as `{data, truncated, next_start, hint}` (a plain array when everything fits, as before); `run_report` keeps its shape and adds `truncated`, `total_rows`, `hint`; one row over the cap is still refused. count_docs (`{count, doctype}`, text unchanged; with `at_least` `{doctype, at_least, result, count}` plus `warning` when the site gave up, result and count then null), whoami (`whoamiResult`, same as its text) and list_sites (`{sites}`, text still the bare array) return `structuredOut`; keep their text byte-identical. Bulk tools send `notifications/progress` per item only when the call had a progress token, best effort (mcp-go queues it without waiting, drops it when the session channel is full, and may write it after the response); `runBulk` stops starting items once ctx is cancelled (`TestMCPBulkCancel`). `bulkTool(n, workers, …)` runs bulk_create/update/delete with the optional `concurrency` argument (`concurrencyArg`, 1 to `maxMCPBulkWorkers` = 4, default 1 = input order, one at a time; anything else is a usage error before any request; parallel items must be independent, which only the caller knows, so the tool descriptions and the safe-bulk-import prompt say so): results are indexed by input position, and the progress counter and its notification share one mutex so the values only go up; with concurrency above 1 `refuseDuplicateNames` (case-insensitive) refuses a bulk_update/bulk_delete that names a document twice, as a usage error before any request. **bulk_create `atomic`** (`atomicCreate`, mcp_tools.go) is `ffc bulk-create --atomic` as a tool: one `client.InsertMany`, items checked first by `client.InsertManyDocs` (a foreign `doctype` or `parent`+`parenttype` is a usage error) and `atomicLimit` = min(`maxMCPBulkItems`, `client.MaxInsertMany`) = 200 ("too many items"); a `concurrency` argument with a value is a usage error (null counts as absent); `atomicArg` reads the flag strictly (bool or "true"/"false", anything else is a usage error, never false, because that would create one by one when all or none was asked). The result is `createdReport(names).JSON()`, the shape of a per-item run (shared with the CLI); a failure is `atomicError(err)` as a tool error ("nothing was created" / "probably created" / "may or may not have been created"; its `--timeout` hint is the `ffc mcp` process's), no report. No progress notifications (one request). Policy and audit are the tool's own (scope = doctype). bulk_submit/bulk_cancel (mcp_lifecycle_tools.go) have no `concurrency`: they reuse `lifecycleBulk.op` of the CLI commands with one worker (deadlocks on GL/stock postings, cancel order), after `refuseWorkflowFor(…, mcp=true)` once; the MCP messages name apply_workflow and amend_doc instead of ffc commands. `scopeOf` refuses a present but empty `doctype` (`policy: the doctype argument is empty`; it would add nothing to the scope and skip allow/deny_doctypes) except for `optionalDoctype` tools (search, list_errors). A new tool needs an entry in both `toolActions` and `toolSurface`. **T2.7 completion:** the `big` read tools (`jqTool`: big and `actRead`, so a failing filter never hides a write) declare `jq` (added by `describeTools`; `mcp_jq.go`). `jqArg` checks it in `env.run` after the site is read (so the audit line names it) and before scope, policy and any request (bad query or tool without it: `auditInvalid`). `runJQ` runs it in a child process: `os.Executable()` with only `FFC_JQ_CHILD=ffc-mcp-jq-v1` in its environment, handled in `Execute()` (and `TestMain`) before cobra, `jqChild` reads `{query, input}`, a watchdog exits 3 past 256 MiB heap, the parent kills it at `jqTimeout` (5 s) and reads at most twice the result cap. In-process gojq checks ctx only between steps and has no memory bound (`"a" * 2e9`, `def f: [f]; f` reached GBs). A failure after the read is `auditError`. The result always goes through `marshalResult` (JSON, 512 KiB cap; a bare string would have skipped it). gojq compiled without options has no `$ENV`, `input` or modules. One output as is, none or several as an array. `response_format` (`concise`/`detailed`) on list_docs (`detailed` without fields = `["*"]`, set after scopeOf, which only refuses dotted/backtick names) and run_report (`detailed` = raw result, still `limitReportRows`/`fitReportRows`). Cache hints: `mcpServerOptions` sets `WithMethodCacheHints` (1 h, private) on tools/prompts/resources/templates lists and server/discover; resources/read keeps mcp-go's 0. Not done on purpose: `outputSchema` for list_docs (array or truncation envelope) and get_schema (open object): a strict schema would make clients reject valid results.
